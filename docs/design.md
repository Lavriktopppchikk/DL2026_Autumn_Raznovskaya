# Проектирование: QR Studio (Задание 3 — генератор QR-кодов)

![Главный экран](images/01-main.png)

## 1.1. Пользовательские сценарии
1. **Быстрый QR для ссылки.** Как владелец кофейни, я хочу вставить ссылку на меню и сразу увидеть QR-код, чтобы распечатать его и положить на столы.
2. **Фирменный стиль.** Как маркетолог, я хочу задать цвета, размер и загрузить логотип в центр кода, чтобы QR соответствовал бренду, и скачать его в PNG (для печати) или SVG (для масштабирования).
3. **Возврат к прошлому.** Как пользователь, я хочу сохранить код в историю и скопировать постоянную ссылку на картинку, чтобы позже вернуться к нему, поделиться или отредактировать.

## 1.2. Функциональные требования
**Обязательные**
- Frontend: ввод ссылки или текста, выбор типа (URL/текст); цвета кода и фона; размер; загрузка логотипа; живое превью (debounce 300 мс); кнопки «Скачать PNG/SVG» и «Сохранить и скопировать ссылку»; список истории; показ ошибок валидации.
- Backend: генерация PNG/SVG; валидация URL (http/https + host), цветов (#RRGGBB), размера (128–1024), логотипа (картинка, ≤1 МБ); сохранение, выдача и удаление истории; постоянная ссылка на картинку.

**Опциональные (реализовано)**
- Предупреждение о низком контрасте цветов (WCAG < 3).
- Автоповышение уровня коррекции ошибок до H при наличии логотипа.

**Опциональные (не реализовано, идеи на будущее)**
- Динамические QR-коды (редирект через сервер) и статистика сканирований, vCard, серии кодов, аккаунты пользователей.

## 1.3. Проектирование API
Авторизации нет (один пользователь, история общая) — осознанное упрощение для тестового задания.

| Метод | Путь | Запрос | Ответ |
|---|---|---|---|
| POST | `/api/qr` | JSON `{data, kind: "url"\|"text", fg, bg, size, format: "png"\|"svg", logo?: dataURL}` | `200` изображение (`image/png` или `image/svg+xml`); `422 {detail}` при ошибке валидации |
| POST | `/api/history` | те же поля (без `format`) | `201 {id}` |
| GET | `/api/history` | — | `200 [{id, data, kind, fg, bg, has_logo, created_at}]` (последние 50) |
| GET | `/api/history/{id}` | — | `200` полная запись (с `logo`); `404` |
| DELETE | `/api/history/{id}` | — | `204`; `404` |
| GET | `/api/qr/{id}.{png\|svg}` | — | изображение, пересобранное из сохранённых настроек (постоянная ссылка) |

## 1.4. Модель данных
SQLite, таблица `qr_codes`:

| Поле | Тип | Описание |
|---|---|---|
| id | INTEGER, PK, AUTOINCREMENT | идентификатор |
| data | TEXT | содержимое QR (до 1000 символов) |
| kind | TEXT | `url` или `text` |
| fg, bg | TEXT | цвета в формате `#RRGGBB` |
| size | INTEGER | желаемый размер в пикселях |
| logo | TEXT, NULL | логотип в виде data URL |
| created_at | INTEGER | время создания (unix) |

Хранятся настройки, а не готовые картинки: файл пересобирается по запросу. Так база остаётся маленькой, а формат (PNG или SVG) выбирается при скачивании.

## 1.5. Ключевые технические решения
- **Backend: Python + FastAPI.** Быстрая разработка, автоматическая валидация через Pydantic, документация на `/docs`, одинаково запускается на Linux и Windows.
- **Генерация: `segno` + `Pillow`.** `segno` — чистый Python, умеет PNG и SVG без системных зависимостей; Pillow нужен только для наложения логотипа на PNG.
- **База данных: SQLite (модуль `sqlite3`).** Не требует настройки, один файл; ORM для одной таблицы избыточен.
- **Frontend: React + Vite.** Удобное состояние для живого превью; Vite проксирует `/api` на бэкенд, поэтому CORS не нужен.
- **Превью строится на сервере**, а не на клиенте: то, что видно на экране, совпадает со скачанным файлом.
- **Логотип и сканируемость:** логотип занимает не более ~20% стороны (~4% площади), под ним подложка цвета фона, уровень коррекции ошибок H.
- **Внешние API не используются.**
- **Ограничения:** нет авторизации и rate limiting, история общая, логотип хранится в БД как data URL.
